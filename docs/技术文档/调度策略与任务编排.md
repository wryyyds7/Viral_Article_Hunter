## 一、核心任务链

### 1.1 主链路（采集驱动）

```
用户发起采集 → 采集任务入队 → 采集执行(异步) → 采集完成
                                                    │
                                                    ▼
                                          自动触发爆款分析(异步)
                                                    │
                                                    ▼
                                          分析完成 → 主动通知用户
                                                    │
                                                    ▼
                                          用户选择素材 → 触发改写
                                                    │
                                                    ▼
                                          改写执行(并行异步) → 逐平台完成
                                                    │
                                                    ▼
                                          全部完成 → 主动通知用户
```

### 1.2 辅链路（上传驱动）

```
用户上传文档 → 文件解析(异步) → 解析完成 → 数量阈值判断
                                              │
                              ┌───────────────┼───────────────┐
                              ▼               ▼               ▼
                         ≥10篇自动      <10篇提醒后      用户取消
                          触发分析       用户确认触发
                              │               │
                              └───────┬───────┘
                                      ▼
                               爆款分析(异步) → 同主链路
```

### 1.3 一键链路（用户说一句话，Agent自动编排）

```
用户："帮我做一期小红书内容"
  │
  ▼
Agent拆解：
  1. 检查今日已采集？→ 否则触发采集
  2. 筛选评分>70的素材 → 按小红书适配度排序
  3. 取Top1分析 → 生成小红书版改写
  4. 推送结果 + 建议
```

## 二、任务状态机

### 2.1 通用任务状态

| 状态 | 说明 | 可流转到 |
|------|------|----------|
| `pending` | 等待执行 | `running`、`cancelled` |
| `running` | 执行中 | `completed`、`failed`、`partial` |
| `completed` | 全部完成 | — |
| `partial` | 部分完成（多子任务时有部分失败） | `completed`（重试后） |
| `failed` | 全部失败 | `running`（重试） |
| `cancelled` | 用户取消 | `pending`（重新入队） |

### 2.2 各模块状态流转

#### 采集任务

```
pending → running → completed
                  → partial（部分平台失败，有降级数据）
                  → failed（全部平台失败）
         → cancelled
```

#### 分析任务

```
pending → running → completed
                  → failed（LLM调用失败）
         → cancelled
```

#### 改写任务

```
pending → running → partial（部分平台完成，部分失败）
                  → completed（全部平台完成）
                  → failed（LLM调用失败，0个平台成功）
         → cancelled
每个平台结果独立：pending → running → completed / failed
```

## 三、自动推进规则

### 3.1 触发条件与动作

| 事件 | 自动动作 | 通知用户 |
|------|----------|----------|
| 采集任务状态变为 completed/partial | 自动创建分析任务 | 否（等分析完一起通知） |
| 分析任务状态变为 completed | 无（等用户选择改写） | 是："N篇分析完成，M篇值得改写" |
| 上传文件全部解析完成 | 检查数量阈值，≥10自动创建分析任务 | 是："N篇文档解析完成，正在分析..." |
| 上传文件全部解析完成（<10篇） | 不自动触发分析 | 是："N篇解析完成，建议补到10篇" |
| 改写某平台完成 | 更新该平台状态 | 否（等全部完成） |
| 改写任务全部完成 | 无 | 是："7平台改写完毕" |

### 3.2 不自动推进的场景

| 场景 | 原因 | 用户操作 |
|------|------|----------|
| 分析完成后不自动改写 | 用户可能只想看分析，不一定改写 | 用户手动选择素材→改写 |
| 改写完成后不自动导出 | 用户可能要编辑改写结果再导出 | 用户手动导出 |
| 采集失败后不自动重试 | 可能是配置/API问题，重试也会失败 | 用户手动重试或调整参数 |

## 四、异步执行策略

### 4.1 任务队列设计

```
┌─────────────┐     ┌──────────────┐     ┌───────────────┐
│  API层       │────▶│  任务调度器    │────▶│  Worker池      │
│  (FastAPI)   │     │  (APScheduler)│     │  (asyncio)     │
└─────────────┘     └──────────────┘     └───────────────┘
                           │                     │
                    ┌──────┼──────┐        ┌──────┼──────┐
                    ▼      ▼      ▼        ▼      ▼      ▼
                 collect analyze rewrite  collect analyze rewrite
                 queue   queue  queue    worker  worker  worker
```

### 4.2 并发控制

| 任务类型 | 最大并发 | 排队策略 | 说明 |
|----------|----------|----------|------|
| 采集任务 | 3 | FIFO | 外部API有调用频率限制 |
| 分析任务 | 5 | 优先级(高分素材优先) | LLM调用有Token速率限制 |
| 改写任务 | 7 | 用户优先级+平台并行 | 7平台并行，受LLM并发限制 |
| 文件解析 | 10 | FIFO | CPU密集但量小，可高并发 |

### 4.3 长任务超时

| 任务类型 | 超时时间 | 超时处理 |
|----------|----------|----------|
| 单平台采集 | 30秒 | 标记该平台失败，不影响其他平台 |
| 单篇分析 | 60秒 | 标记该篇失败，继续分析下一篇 |
| 单平台改写 | 90秒 | 标记该平台失败，继续其他平台 |
| 文件解析 | 30秒/文件 | 标记该文件失败，继续解析下一个 |

## 五、降级策略

### 5.1 采集降级（已有三级，补充细节）

| 级别 | 触发条件 | 动作 | 用户感知 |
|------|----------|------|----------|
| L1-主源 | 默认 | 调用官方API/红狐数据 | 正常数据 |
| L2-备用源 | L1超时>10秒或返回错误 | 切换搜索引擎采集 | 数据可能有延迟 |
| L3-上传导入 | L1+L2全部不可用 | 提示用户上传文档 | "平台暂不可用，可上传文档替代" |

### 5.2 分析降级

| 场景 | 降级动作 | 用户感知 |
|------|----------|----------|
| LLM调用超时 | 重试1次，仍超时则用规则引擎生成基础评分 | "AI深度分析暂不可用，已用快速评分替代" |
| LLM返回格式错误 | 用正则提取关键信息，补全默认值 | "分析部分完成，部分标签需要人工确认" |
| LLM服务完全不可用 | 只做规则评分（热度公式+关键词匹配） | "AI分析服务维护中，已用基础评分替代" |

### 5.3 改写降级

| 场景 | 降级动作 | 用户感知 |
|------|----------|----------|
| 某平台改写失败 | 跳过该平台，其余平台正常 | "6/7平台改写完成，{平台}失败" |
| 全部平台失败 | 提示用户稍后重试 | "改写服务暂不可用，请稍后重试" |
| 相似度>60% | 自动追加一轮调整 | "去重校验未通过，已自动优化"（最多重试2次） |

### 5.4 整体降级（LLM服务宕机）

```
LLM不可用时：
├── 采集：正常运行（不依赖LLM）
├── 分析：降级为规则引擎评分
├── 改写：暂停服务，提示用户
└── 上传解析：正常运行（不依赖LLM）
```

## 六、错误恢复

### 6.1 断点续传

| 任务类型 | 断点记录 | 恢复策略 |
|----------|----------|----------|
| 批量采集 | 已完成的平台列表 | 从未完成的平台开始，不重复采集 |
| 批量分析 | 已分析的文章ID列表 | 从未分析的文章开始 |
| 多平台改写 | 已完成的平台列表 | 从未完成的平台开始 |
| 批量上传 | 已解析的文件列表 | 从未解析的文件开始 |

### 6.2 自动重试

| 场景 | 重试次数 | 重试间隔 | 条件 |
|------|----------|----------|------|
| 外部API超时 | 2次 | 5秒、15秒 | 非认证错误 |
| LLM调用失败 | 1次 | 10秒 | 非Token超限 |
| 数据库写入失败 | 3次 | 1秒、3秒、5秒 | 连接类错误 |
| 文件解析失败 | 0次 | — | 不重试，标记失败让用户处理 |

### 6.3 任务恢复流程

```
服务重启后：
1. 查询所有 status=running 的任务
2. 检查任务最后心跳时间
   ├── <5分钟：标记为 running，恢复执行
   ├── 5-30分钟：标记为 pending，重新入队
   └── >30分钟：标记为 failed，通知用户
3. 对 partial 状态的任务，重试失败的子任务
```

## 七、进度追踪

### 7.1 进度模型

每个异步任务返回 `task_id`，前端通过轮询或SSE获取进度：

```json
{
  "task_id": "uuid",
  "type": "collect | analyze | rewrite | upload",
  "status": "running",
  "progress": {
    "total": 12,
    "completed": 5,
    "failed": 1,
    "pending": 6
  },
  "eta_seconds": 45,
  "started_at": "2026-06-04T10:00:00Z",
  "results_preview": []  // 已完成的部分结果
}
```

### 7.2 轮询策略

| 阶段 | 轮询间隔 | 说明 |
|------|----------|------|
| 任务刚创建 | 1秒 | 快速获得初始状态 |
| 执行中 | 3秒 | 平衡实时性和服务器压力 |
| 即将完成(>80%) | 1秒 | 减少用户等待感知 |
| 任务完成 | 停止轮询 | 前端收到完成状态后停止 |

### 7.3 SSE推送（改写模块优先实现）

改写任务支持SSE流式推送，每完成一个平台推送一次：

```
event: platform_complete
data: {"platform": "xiaohongshu", "status": "completed", "content": "..."}

event: platform_complete
data: {"platform": "zhihu", "status": "completed", "content": "..."}

event: task_complete
data: {"status": "completed", "total": 7, "success": 6, "failed": 1}
```
