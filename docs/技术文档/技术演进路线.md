# 爆文猎人 — 技术演进路线

| 字段 | 内容 |
|------|------|
| 文档版本 | v1.0 |
| 创建日期 | 2026-06-04 |
| 原则 | 不提前引入当前规模不需要的中间件，每一项升级都有明确的触发条件和量化指标 |

---

## 核心原则

**按需演进，数据驱动。** 不为"可能需要"买单，只为"已经遇到"投入。

每项升级必须同时满足：
1. **触发条件**：当前方案已达到性能/可靠性上限
2. **量化指标**：有可观测的数据证明瓶颈存在
3. **收益明确**：升级后能解决什么具体问题

---

## 演进总览

```
MVP                        v1.1                      v2.0
(0-100 用户)              (100-1000 用户)           (1000+ 用户)
─────────────────────────────────────────────────────────────
asyncio.Queue          →  Celery + Redis          →  Celery 多 Worker 分组
TTLCache 进程内缓存     →  Redis 缓存层            →  Caffeine + Redis 多级缓存
PostgreSQL 直读         →  PG + Redis 热点缓存      →  PG 读写分离
内存滑动窗口限流        →  Redis 限流计数器         →  Redis + 令牌桶集群限流
单实例部署              →  双实例 + Nginx           →  多实例 + K8s 弹性伸缩
pg_trgm 模糊搜索        →  zhparser 中文分词        →  pgvector 语义搜索
日志文件                →  日志文件 + 基础监控       →  ELK + Prometheus + Grafana
```

## 一、MVP 阶段（当前，0-100 用户）

### 1.1 架构现状

```
Client
  │
  ▼
Nginx (反向代理 + SSL)
  │
  ▼
FastAPI (单实例, uvicorn 4 workers)
  │
  ├── asyncio.Queue (进程内任务队列)
  ├── TTLCache (进程内缓存, 最大500条, TTL 5分钟)
  ├── APScheduler (定时采集)
  │
  ▼
PostgreSQL 16 (单实例, 直读直写)
```

### 1.2 各模块当前方案

| 模块 | 当前方案 | 能力上限 | 潜在风险 |
|------|----------|----------|----------|
| 任务队列 | `asyncio.Queue` | 单进程，无持久化 | 进程重启任务丢失 |
| 缓存 | `TTLCache(maxsize=500, ttl=300)` | 单进程，500条 | 缓存命中率依赖单进程 |
| 限流 | 内存滑动窗口 | 单实例 | 多实例部署时限流失效 |
| 数据库 | PostgreSQL 直读 | ~500 QPS | 热点查询慢 |
| 搜索 | `pg_trgm` GIN 索引 | 模糊匹配，无语义 | 中文分词不精准 |
| 部署 | 单实例 Docker | 单点故障 | 无容灾 |
| 监控 | 日志文件 + `tail` | 人工巡检 | 问题发现滞后 |

### 1.3 MVP 不引入的技术及原因

| 技术 | 解决的问题 | 不引入的原因 |
|------|-----------|-------------|
| Redis 分布式缓存 | 降低 DB 访问 | 100 用户下 PG 直读 QPS < 50，无压力 |
| RabbitMQ / Celery | 任务持久化+跨进程 | 进程内队列够用，任务丢失可接受（用户可重试） |
| Canal 监听 binlog | 缓存一致性 | 没有分布式缓存，不存在一致性问题 |
| 布隆过滤器 | 防缓存穿透 | 有认证门禁，不存在恶意查询 |
| 互斥锁+逻辑过期 | 防缓存击穿 | 没有热 key，不存在击穿风险 |
| Lua 原子扣减 | 防超卖 | 无秒杀场景，配额用 DB 事务即可 |
| 一致性哈希 | 缓存分片 | 单 Redis 实例够用（v1.1 才引入 Redis） |
| K8s | 弹性伸缩 | 用户量不到，运维成本 > 收益 |

## 二、v1.1 阶段（100-1000 用户）

### 2.1 触发条件

升级到 v1.1 需要 **同时满足以下至少 3 项**：

| 序号 | 指标 | 阈值 | 监测方式 |
|------|------|------|----------|
| 1 | 注册用户数 | ≥ 100 | `SELECT COUNT(*) FROM users` |
| 2 | 日活用户数(DAU) | ≥ 30 | 日登录统计 |
| 3 | 共享文章列表查询 P95 | > 200ms | 请求日志统计 |
| 4 | 任务丢失（进程重启后） | 用户投诉 ≥ 2 次 | 反馈记录 |
| 5 | LLM 日均调用量 | > 500 次 | `SUM(llm_tokens_used)` |
| 6 | 采集任务并发排队 | 等待 > 30s | 任务队列深度监控 |

### 2.2 升级项

#### 升级1：Celery + Redis 任务队列（替代 asyncio.Queue）

```
升级前:
  FastAPI → asyncio.Queue → Worker(进程内)

升级后:
  FastAPI → Celery Client → Redis(Broker) → Celery Worker(独立进程)
                                          ↗ 可横向扩展多 Worker
```

| 维度 | 升级前(asyncio.Queue) | 升级后(Celery + Redis) |
|------|----------------------|----------------------|
| 持久化 | 进程重启任务丢失 | Redis 持久化，重启不丢 |
| 横向扩展 | 只能单进程 | 可启动多个 Worker 进程 |
| 任务监控 | 无 | Flower Dashboard |
| 定时任务 | APScheduler | Celery Beat（更可靠） |
| 重试策略 | 手动实现 | Celery 内置 exponential backoff |

**Worker 分组策略**：

| 队列名 | 并发数 | 任务类型 | 说明 |
|--------|--------|----------|------|
| `collect` | 3 | 采集任务 | 外部API限流，低并发 |
| `analyze` | 5 | 分析任务 | LLM 速率限制 |
| `rewrite` | 7 | 改写任务 | 多平台并行 |
| `parse` | 10 | 文件解析 | CPU 密集但量小 |
| `default` | 5 | 其他 | 通知/导出/统计 |

**成本**：+1 Redis 实例，+Celery 依赖。

#### 升级2：Redis 缓存层

```python
# 缓存策略：Cache-Aside + TTL
async def get_shared_articles(query, page, page_size):
    # 1. 查 Redis
    cache_key = f"articles:{hash(query)}:{page}:{page_size}"
    cached = await redis.get(cache_key)
    if cached:
        return json.loads(cached)
    
    # 2. 查 DB
    result = await db_query(...)
    
    # 3. 写 Redis (TTL 5分钟)
    await redis.setex(cache_key, 300, json.dumps(result))
    return result
```

**缓存对象与 TTL**：

| 缓存对象 | TTL | 更新策略 |
|----------|-----|----------|
| 共享文章列表 | 5 分钟 | TTL 过期 + 采集完成后主动刷新 |
| 单篇分析结果 | 30 分钟 | TTL 过期（分析结果不变） |
| 系统配置 | 10 分钟 | 管理员修改后主动刷新 |
| 用户配额 | 1 分钟 | 每次操作后更新 |
| 限流计数器 | 1 分钟滑动窗口 | 实时计数 |

**一致性方案**：不引入 Canal，采用 **TTL 过期 + 关键事件主动刷新**：

```
采集完成 → 删除 articles:* 缓存 → 下次查询重新加载
管理员改配置 → 删除 config:* 缓存
用户操作 → 更新 quota 缓存
```

**为什么不用 Canal**：我们的写操作频率极低（采集每小时几次，配置变更每天几次），主动刷新完全够用。Canal 是给"每秒数千次写操作"的场景准备的。

#### 升级3：Redis 限流计数器

```python
# 替代内存滑动窗口，支持多实例部署
async def check_rate_limit(key: str, limit: int, window: int = 60):
    """Redis 滑动窗口限流"""
    now = time.time()
    pipe = redis.pipeline()
    pipe.zremrangebyscore(key, 0, now - window)  # 清理过期
    pipe.zadd(key, {str(now): now})                # 加入当前请求
    pipe.zcard(key)                                 # 计数
    pipe.expire(key, window)
    _, _, count, _ = await pipe.execute()
    return count <= limit
```

#### 升级4：zhparser 中文分词搜索

```sql
-- 替代 pg_trgm，支持中文语义分词
CREATE EXTENSION zhparser;
CREATE TEXT SEARCH CONFIGURATION zh (PARSER = zhparser);
ALTER TEXT SEARCH CONFIGURATION zh ADD MAPPING FOR n,v,a,i,e,l WITH simple;

-- article 表新增 tsvector 列
ALTER TABLE article ADD COLUMN search_vector tsvector
    GENERATED ALWAYS AS (
        setweight(to_tsvector('zh', coalesce(title, '')), 'A') ||
        setweight(to_tsvector('zh', coalesce(content, '')), 'B')
    ) STORED;

CREATE INDEX idx_article_search ON article USING GIN(search_vector);
```

| 维度 | pg_trgm (MVP) | zhparser (v1.1) |
|------|---------------|-----------------|
| 分词 | 按字符 trigram | 中文语义分词 |
| "职场干货" | 匹配含"职""场""干""货"的 | 匹配"职场""干货"语义 |
| 精准度 | 低（大量无关结果） | 高（理解词义） |
| 索引大小 | 大（trigram膨胀） | 小（tsvector压缩） |

#### 升级5：双实例部署 + Nginx 负载均衡

```
                    ┌─────────────┐
                    │   Nginx     │
                    │  (upstream) │
                    └──────┬──────┘
                           │
                 ┌─────────┼─────────┐
                 │                   │
           ┌─────┴─────┐     ┌─────┴─────┐
           │ FastAPI    │     │ FastAPI    │
           │ :8000      │     │ :8001      │
           └────────────┘     └────────────┘
                 │                   │
                 └─────────┬─────────┘
                           │
                    ┌──────┴──────┐
                    │ PostgreSQL  │
                    │ + Redis     │
                    └─────────────┘
```

Nginx 配置要点：
- `upstream` 轮询 + 健康检查
- 静态资源由 Nginx 直接服务（不经过 FastAPI）
- SSE 长连接：`proxy_read_timeout 300s`
- WebSocket 支持（预留）

#### 升级6：基础监控

| 监控项 | 工具 | 告警通道 |
|--------|------|----------|
| API 响应时间 | 自定义中间件 + 日志 | 邮件 |
| 错误率 | 日志统计脚本 | 邮件 |
| Celery 队列深度 | Flower API | 邮件 |
| Redis 内存 | `redis-cli info` | 邮件 |
| PG 慢查询 | `pg_stat_statements` | 邮件 |

**为什么不上 Prometheus**：v1.1 监控项不多，日志 + 简单脚本够用，Prometheus + Grafana 的部署维护成本暂不划算。

### 2.3 v1.1 不引入的技术

| 技术 | 原因 |
|------|------|
| 多级缓存(Caffeine+Redis) | Redis 单层缓存命中率 > 95%，够用 |
| 布隆过滤器 | 认证门禁 + Redis 缓存空值，穿透问题不严重 |
| RabbitMQ | Celery + Redis 方案更轻量，少维护一个中间件 |
| K8s | 双实例 Docker Compose 够用 |
| PG 读写分离 | 读 QPS < 1000，单主库够 |

## 三、v2.0 阶段（1000+ 用户）

### 3.1 触发条件

升级到 v2.0 需要 **同时满足以下至少 3 项**：

| 序号 | 指标 | 阈值 | 监测方式 |
|------|------|------|----------|
| 1 | 注册用户数 | ≥ 1000 | DB 统计 |
| 2 | 日活用户数(DAU) | ≥ 300 | 登录统计 |
| 3 | API P95 响应时间 | > 500ms | APM 监控 |
| 4 | PG 慢查询占比 | > 5% | pg_stat_statements |
| 5 | Redis 内存使用 | > 4GB | redis-cli info |
| 6 | 单 Worker 处理延迟 | > 60s | Celery Flower |

### 3.2 升级项

#### 升级1：Caffeine + Redis 多级缓存

```
请求 → Caffeine(L1, 进程内, 1000条, 1分钟TTL)
         │ miss
         ▼
       Redis(L2, 分布式, 50000条, 5分钟TTL)
         │ miss
         ▼
       PostgreSQL
```

| 缓存层 | 命中率 | 响应时间 | 容量 |
|--------|--------|----------|------|
| L1 Caffeine | ~60% | < 1ms | 1000 条 |
| L2 Redis | ~35% | < 5ms | 50000 条 |
| DB | ~5% | 30-100ms | 全量 |

**一致性策略**：
- L1 → L2：TTL 短(1分钟)，过期自动从 L2 更新
- L2 → DB：关键事件主动删除 + TTL 保底
- 仍不引入 Canal：写频率仍然不高，主动刷新够用

#### 升级2：PG 读写分离

```
写入 → PG Primary
读取 ← PG Primary + 2 个 Replica
              ↑
        PgBouncer 连接池
```

| 组件 | 作用 |
|------|------|
| PG Primary | 所有写操作 |
| PG Replica ×2 | 读操作（共享文章列表/分析结果/看板统计） |
| PgBouncer | 连接池管理，避免连接数耗尽 |

**触发条件**：慢查询日志显示读操作占比 > 80% 且 P95 > 300ms。

#### 升级3：pgvector 语义搜索

```sql
-- v1.1 的 zhparser 关键词匹配 → v2.0 的语义向量搜索
CREATE EXTENSION vector;

-- article 表新增向量列
ALTER TABLE article ADD COLUMN embedding vector(1536);

-- 创建 HNSW 索引
CREATE INDEX idx_article_embedding ON article 
    USING hnsw (embedding vector_cosine_ops);

-- 语义搜索：找到与查询最相似的10篇文章
SELECT id, title, 1 - (embedding <=> query_vector) AS similarity
FROM article
ORDER BY embedding <=> query_vector
LIMIT 10;
```

| 维度 | zhparser (v1.1) | pgvector (v2.0) |
|------|-----------------|-----------------|
| 查询方式 | 关键词精确匹配 | 语义相似度匹配 |
| "怎么涨粉" | 只匹配含"涨粉"的文章 | 匹配"粉丝增长""账号运营""流量提升" |
| 准确率 | 中 | 高 |
| 成本 | 低 | 需要调用 Embedding API |

#### 升级4：HyperLogLog UV 统计

```python
# 替代 COUNT(DISTINCT user_id)
# 内存占用从 O(N) 降到 O(1)，精度 0.81%

async def record_uv(date: str, user_id: str):
    await redis.pfadd(f"uv:{date}", user_id)

async def get_uv(date: str) -> int:
    return await redis.pfcount(f"uv:{date}")
```

| 维度 | COUNT(DISTINCT) | HyperLogLog |
|------|-----------------|-------------|
| 1万 UV 内存 | ~500KB | ~12KB |
| 100万 UV 内存 | ~50MB | ~12KB |
| 精度 | 100% | 99.19% |
| 查询速度 | 慢(全表扫描) | 快(O(1)) |

#### 升级5：K8s 弹性伸缩

```
当 Celery 队列深度 > 100 持续 5 分钟
  → HPA 自动扩容 Worker Pod
  → 最少 2 副本，最多 10 副本

当 队列深度 < 10 持续 10 分钟
  → HPA 自动缩容
```

```
Prometheus (指标采集)
```

## 四、升级决策流程

每次升级前必须走以下流程：

```
1. 发现瓶颈
   └── 通过监控数据/用户反馈/日志分析确认问题存在

2. 量化评估
   └── 当前指标 vs 目标指标，差距有多大

3. 方案选择
   └── 列出 2-3 个方案，评估：效果/成本/风险/回滚难度

4. 灰度上线
   └── 先在 1 个实例验证 → 25% 流量 → 50% → 100%

5. 效果验证
   └── 上线后对比关键指标，确认收益达标

6. 文档更新
   └── 更新技术方案文档 + 项目结构文档
```

## 六、不可演进项（始终不需要）

以下技术在爆文猎人的业务模型下没有适用场景，无论用户量多大都不需要引入：

| 技术 | 不需要的原因 |
|------|-------------|
| Canal 监听 binlog | 写频率低，主动刷新 + TTL 够用，复杂度不值得 |
| 布隆过滤器 | 认证门禁已过滤恶意请求，Redis 缓存空值防穿透 |
| Lua 原子扣库存 | 无秒杀场景，配额扣减用 DB 事务 |
| Feed 流推拉结合 | 非社交产品，无关注/推送 |
| Redis GEO 附近搜索 | 无地理位置功能 |
| 一致性哈希分片 | Redis 单实例到 v2.0 仍够用，分片复杂度不值得 |
| RabbitMQ | Celery + Redis 更轻量，Python 生态原生 |
| 分布式事务(Seata/TCC) | 无跨服务事务需求 |
