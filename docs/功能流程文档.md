## 二、核心业务流程

### 2.1 主链路：采集 → 分析 → 改写

```
[用户] 点击"采集热点" → 选择平台 + 输入关键词
    │
    ▼
POST /v1/collect          ←── 创建采集任务(collection_task)
    │
    ▼
[调度器] 任务入队，异步执行
    │
    ├── 调用红狐API(小红书/公众号)   ←── honghu_collector.py
    ├── 调用搜索API(头条/知乎/B站)   ←── search_collector.py
    │
    ▼
采集完成 → 文章批量写入 article 表(collection_method='api')
    │
    ▼
[EventBus] 发出 collect.completed 事件
    │
    ▼
[自动触发] 创建分析任务(analysis_result)
    │
    ▼
[LLM] 逐篇调用分析 Prompt → 输出爆款基因 JSON
    │
    ▼
[适配层] 格式清洗 → Schema校验 → 字段映射 → 业务校验
    │
    ▼
分析结果写入 analysis_result 表
    │
    ▼
[EventBus] 发出 analyze.completed 事件
    │
    ▼
[通知用户] "N篇分析完成，M篇值得改写"
    │
    ▼
[用户] 查看分析结果 → 选择素材 → 点击"改写" → 选择目标平台 + 调参
    │
    ▼
POST /v1/rewrite          ←── 创建改写任务(rewrite_task)
    │
    ▼
[调度器] 多平台并行改写(最多7个平台)
    │
    ▼
[LLM] 逐平台调用改写 Prompt + 注入平台规则
    │                         ↓
    │              ┌── xiaohongshu.md 规则
    │              ├── zhihu.md 规则
    │              ├── bilibili.md 规则
    │              ├── douyin.md 规则
    │              ├── kuaishou.md 规则
    │              ├── wechat.md 规则(公众号)
    │              └── wechat_video.md 规则(视频号)
    │
    ▼
每个平台完成 → [SSE推送] event: platform_complete
    │
    ▼
[质量自检] 相似度检查(≤0.6) + 平台风格检查
    │   ├── 不通过 → 自动追加一轮调整(最多2次)
    │   └── 通过 → 写入 rewrite_result 表
    │
    ▼
全部平台完成 → [EventBus] rewrite.completed
    │
    ▼
[通知用户] "7平台改写完毕"
    │
    ▼
[用户] 查看/编辑改写结果 → 导出(MD/Word/ZIP)
```

### 2.2 辅链路：上传 → 分析 → 改写

```
[用户] 点击"上传文档" → 选择文件(TXT/MD/DOCX/PDF/HTML)
    │
    ▼
POST /v1/upload/batch     ←── 创建上传批次(upload_batch)
    │
    ▼
逐文件异步解析
    │
    ├── txt/md  → TxtParser       (chardet检测编码 → 读取全文)
    ├── docx    → DocxParser      (python-docx提取段落)
    ├── pdf     → PdfParser       (pdfplumber提取文本)
    └── html    → HtmlParser      (BeautifulSoup去标签)
    │
    ▼
解析成功 → 写入 upload_file(parsed_title, status='success')
         → 创建 article(collection_method='upload', upload_file_id=xxx)
    │
    解析失败 → 写入 upload_file(status='failed', error_message=xxx)
    │
    ▼
批次内全部文件处理完毕
    │
    ▼
[阈值判断] success_count >= 10 ?
    │
    ├── 是 → threshold_met=true → [自动触发] 创建分析任务
    │         [EventBus] upload.parsed → "N篇文档解析完成，正在分析..."
    │
    └── 否 → threshold_met=false → [不自动触发]
              [EventBus] upload.parsed_below_threshold
              → [通知用户] "N篇解析完成，建议补到10篇以获得更准确的分析"
              → 用户确认后手动触发: POST /v1/upload/batches/{id}/analyze
    │
    ▼
分析 → 改写（同主链路）
```

### 2.3 素材库管理流程

```
article 表中的素材
    │
    ├── 来源1：采集入库（collection_method='api'/'crawl'，user_id=NULL，共享）
    ├── 来源2：上传入库（collection_method='upload'，user_id=当前用户，私有）
    │
    ▼
素材库操作
    │
    ├── 搜索：全文搜索(pg_trgm GIN索引) + 标签筛选(TEXT[] GIN索引) + 平台筛选
    ├── 排序：热度评分 / 采集时间 / 分析评分
    ├── 收藏：P0 is_favorited布尔 → P1 favorites多分组关联表
    ├── 标签：自动标签(LLM) + 手动标签
    ├── 批量操作：批量分析 / 批量删除 / 批量导出
    └── 导出：单篇MD/Word → 多篇ZIP打包
```

### 2.4 数据看板流程

```
GET /v1/dashboard/overview    ←── 聚合查询
    │
    ├── 今日热点速览
    │   ├── 今日采集数: COUNT(article WHERE collected_at = today)
    │   ├── S/A级文章数: COUNT(analysis_result WHERE hotness_score.level IN ('S','A'))
    │   └── 待分析素材数: COUNT(article LEFT JOIN analysis_result WHERE analysis IS NULL)
    │
    ├── 趋势图表(7天/30天/90天)
    │   ├── 每日采集量趋势
    │   ├── 各平台热度分布
    │   └── 情绪标签分布变化
    │
    ├── 平台对比
    │   └── 各平台文章数 / 平均热度 / 互动数据
    │
    └── 创作统计
        ├── 改写次数 / 成功率
        └── LLM Token 消耗
```

### 2.5 设置页流程

```
设置页
    │

    │   ├── 填入 LLM API Key → AES-256加密存储 → api_keys 表
    │   └── 填入红狐数据 Key → 同上
    │
    ├── 采集计划
    │   ├── 创建定时采集计划 → collection_task + APScheduler
    │   └── 查看计划列表 / 暂停 / 删除

    ├── 改写偏好

    │   ├── 情感强度(1-5)
    │   └── 长度偏好(短/中/长)
    │   → 保存到 user_config 表

        ├── 导出全部数据(JSON/CSV)
```

## 四、认证流程

```
注册：POST /v1/auth/register
  → 校验邮箱格式 + 密码强度(≥8位,字母+数字)
  → 检查邮箱唯一性
  → bcrypt哈希(cost=12) → 写入 users 表
  → 首个用户自动设为 admin
  → 初始化 user_quota 默认配额
  → 返回 Access Token(2h) + Refresh Token(30d, HttpOnly Cookie)

登录：POST /v1/auth/login
  → 查询用户 + bcrypt验证
  → 连续5次失败 → 锁定15分钟
  → 返回 Access Token + Refresh Token
  → 更新 last_login_at

刷新：POST /v1/auth/refresh
  → 验证 Refresh Token(未过期+未撤销)
  → 生成新 Access Token + 新 Refresh Token
  → 旧 Refresh Token 标记 revoked

注销：POST /v1/auth/logout
  → 撤销当前 Refresh Token
  → 前端清除 Access Token

鉴权：所有 /v1/* 接口（除 auth 路由组外）
  → 请求头 Authorization: Bearer <access_token>
  → get_current_user 依赖注入 → 解析 Token → 注入用户对象
  → admin 路由额外校验: admin_only → user.role == 'admin'
```

## 六、降级流程

```
LLM 服务正常
    │
    ├── 分析：LLM完整6维分析(DAIG+情绪+标题公式+结构+互动+平台适配)
    └── 改写：LLM + 平台规则 + 质量自检

LLM 超时/格式错误
    │
    ├── 分析：重试1次 → 仍失败 → 规则引擎评分(热度公式+关键词匹配)
    │         LLM返回格式错误 → 正则提取 + 补全默认值
    └── 改写：单平台失败 → 跳过，其余继续
              相似度>0.6 → 自动追加一轮调整(最多2次)

LLM 完全不可用
    │
    ├── 采集：正常运行(不依赖LLM)
    ├── 分析：降级为规则引擎(4维公式评分，无AI洞察)
    ├── 改写：暂停服务，提示用户"改写服务维护中"
    └── 上传：正常运行(不依赖LLM)

采集源不可用
    │
    ├── L1-主源(红狐/搜索API)超时 → 切L2-备用源
    ├── L2-备用源也失败 → 提示用户上传文档替代(L3)
    └── 全部不可用 → 维护提示
```

## 七、配额与限流流程

```
请求进入
    │
    ▼
[全局限流] rate_limit中间件 → 滑动窗口计数
    │   采集: 5次/分钟
    │   上传: 5次/分钟
    │   分析: 10次/分钟
    │   改写: 3次/分钟
    │   管理后台: 30次/分钟
    │
    ▼ 通过
[认证] get_current_user → 解析Token
    │
    ▼ 通过
[权限] admin_only(仅admin路由) → 校验role
    │
    ▼ 通过
[配额] quota中间件 → 查询user_quota
    │   检查 daily_xxx_used < daily_xxx_limit
    │   超限 → 返回 429 + Retry-After
    │
    ▼ 通过
[业务逻辑] service层执行
    │
    ▼ 完成
user_quota.daily_xxx_used += 1
```
